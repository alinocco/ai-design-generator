# LLM-агенты и оркестратор

Агенты переводят текст в ограничения. Всё остальное — расстановку, проверку и выбор комнат
для пересчёта — делает код. Поэтому любую ошибку модели видно в списке ограничений, а не
в «кривой» мебели, и её можно измерить.

```
бриф ──► Аналитик брифа ──► Brief + ограничения ─┐
                                                  ├─► Планировщик (CP-SAT) ─► Критик ─► версия N
правка ─► Агент правок ──► ограничения, move ────┘        ▲ только затронутые комнаты
                    │
                    └─► вопрос / «не умею» — ответ без новой версии
```

| Агент | Где | Вход | Выход |
|---|---|---|---|
| Аналитик брифа | `agents/brief_analyst.py` | план (список комнат), текст пожеланий | `Brief` (жильцы, стиль, must-have…) и ограничения `source=brief` |
| Агент правок | `agents/edit_agent.py` | план, текущая расстановка, комментарий | `intent`, ограничения `source=user`, `move`, ответ пользователю |
| Оркестратор | `agents/orchestrator.py` | бриф или правка | новая версия `ProjectState` в `VersionStore`, журнал вызовов LLM |
| Планировщик | `solver/` (код) | план, бриф, ограничения | расстановка |
| Критик | `geometry/clearance.py` (код) | расстановка | ошибки и замечания; по `no_passage` возвращает комнату Планировщику |

## Словарь, с которым работает LLM

Модель не выдумывает форматы: она заполняет JSON по схеме (`agents/drafts.py`).

- **Предметы** — только типы из каталога (`desk`, `wardrobe`, …) или id из текущей расстановки (`r2_desk`).
- **Комнаты** — только id из плана (`r2`).
- **Правила:** `exclude`, `require`, `keep`, `near`, `against_wall`, `min_clearance`, `not_in_swing`, `facing`.
- **Намерение правки:** `change` / `question` / `unsupported`. «Снеси стену», «покрась в зелёный» и «сдвинь на 20 см» — это `unsupported`. Такая правка не создаёт новой версии.
- **`move`** — переставить предмет, не говоря куда. Солвер запрещает предмету снова накрыть
  центр прежнего места, а остальные предметы этой комнаты на время пересчёта фиксируются.

Код проверяет черновик по плану и каталогу:
- русские названия («Рабочий стол») переводит в типы, названия комнат («спальня») — в id;
- id предмета превращает в тип и комнату;
- неизвестное отбрасывает с предупреждением.

Новое правило о том же предмете вытесняет старое: правка «убери стол» отменяет «нужен стол»
из брифа. Нормы (`source=norm`) правками не вытесняются.

Комнаты для пересчёта код выводит из ограничений сам. Список от модели только дополняет их.

## Модель: локально или по API

Настройки — в `.env` (образец — `.env.example`). Код один и тот же.

| | Ollama (по умолчанию) | OpenAI-совместимый API |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | `openai` |
| Запрос | родной `/api/chat`, `format` = JSON-схема | `/chat/completions`, `response_format` |
| Гарантия JSON | декодирование по грамматике схемы | `LLM_JSON_MODE=schema` (если API умеет), `object` или `none` |
| Подходит | Qwen2.5 7B/14B Instruct на Mac M3 16 GB | DeepSeek, OpenRouter (в т. ч. Claude), OpenAI, vLLM, LM Studio |

При любом провайдере ответ проверяет Pydantic. Если проверка не прошла, модель видит свою
ошибку и пробует ещё раз, всего до трёх попыток (`agents/structured.py`).

Для Ollama явно задаётся `num_ctx=8192`. Системный промпт со схемой и словарём занимает около
2–2,5 тыс. токенов, а при меньшем окне Ollama молча обрезает начало промпта.

### Ollama: первый запуск

```bash
# установить Ollama с ollama.com, затем:
ollama pull qwen2.5:7b-instruct
cp .env.example .env
uv run aidesign llm-check                 # связь и валидный JSON
```

## Команды

```bash
# новый проект: план + бриф → версия 1 (projects/demo/v0001.json и .svg)
uv run aidesign brief data/demo/demo_48.json \
    "Живём вдвоём, я работаю из дома — стол у окна. Только душ, ванна не нужна." --project demo

# правки к последней версии → версия 2, 3, …
uv run aidesign comment demo "Шкаф мешает открыть дверь, перенеси его. Кровать не трогай."
uv run aidesign comment demo "Убери телевизор"
uv run aidesign comment demo "Какая площадь у спальни?"   # вопрос: новой версии нет

# метрика агентов
uv run aidesign eval-agents -o out/agents_eval_qwen7b.md
```

Каждый вызов модели записывается в `projects/<id>/llm_log.jsonl`: промпт, ответ, время, токены
и номер версии, к которой он привёл. Пригодится для отчёта и разбора ошибок.

## Как измеряем

Размеченные примеры — `data/agents_eval/`:
- `briefs.jsonl` — 12 брифов;
- `edits.jsonl` — 20 правок к демо-квартире, расстановка зафиксирована в `demo_layout.json`;
- отложенные `briefs_holdout.jsonl` и `edits_holdout.jsonl` (6 + 8).

В каждом примере ожидаемые правила:
- `constraints` должны быть найдены;
- `optional` допустимы, но не обязательны: например, `require shower` к фразе «вместо ванны душ»;
- комната и цель проверяются, только если указаны.

| Метрика | Что значит |
|---|---|
| precision / recall / F1 | лишние и пропущенные правила по всем примерам |
| exact | доля примеров, разобранных без единой ошибки |
| occupants_acc | бриф: верно ли поняты жильцы (взрослые, дети, удалёнка, питомцы) |
| intent_acc | правки: change / question / unsupported |
| move_recall / move_precision | правки: какие предметы переставить |
| first_try_json, failed_json | с первой ли попытки JSON прошёл схему; сколько примеров не удалось разобрать совсем |
| median_s, токены | цена и скорость |

Тест `test_eval_sets_are_consistent` прогоняет разметку через «идеальную» модель и требует 100%.
Так ошибка в самой разметке (несуществующий id, опечатка в типе) ловится до запуска на настоящей модели.

Наборов два:
- `briefs.jsonl` и `edits.jsonl` — **dev**, по их ошибкам правятся промпты;
- `*_holdout.jsonl` — **отложенный**: 6 брифов и 8 правок, по нему ничего не настраивается. Цифры для отчёта
  берём отсюда, иначе метрика будет завышена подгонкой под примеры.

```bash
uv run aidesign eval-agents -o out/agents_eval_dev.md
uv run aidesign eval-agents --split holdout -o out/agents_eval_holdout.md
```

qwen2.5:7b-instruct через Ollama на MacBook M3 16 GB:

| Промпт | Набор | Бриф F1 | Жильцы | Правки F1 | Намерение | Move: полнота / точность | JSON с 1-й попытки | Медиана, с (бриф / правка) |
|---|---|---|---|---|---|---|---|---|
| v1: один пример | dev | 0,88 | 1,00 | 0,67 | 0,90 | 1,00 / 0,40 | 100% | 22,5 / 5,3 |
| v2: несколько примеров + проверки кодом | dev | | | | | | | |
| v2 | holdout | | | | | | | |

Что было не так в v1 и что изменено в v2:

| Ошибка v1 | Пример | Исправление в v2 |
|---|---|---|
| Модель копирует единственный пример из промпта | «пара, работаем из дома» → лишнее «стол у окна»; `move` почти в каждой правке (точность 0,4) | несколько коротких разных примеров на вымышленной квартире; явное «move пустой, если…» |
| Предмет не связывается с комнатой | «убери стол из спальни» → убран обеденный стол из гостиной | предметы в промпте сгруппированы по комнатам; «сначала найди комнату, потом предмет в ней» |
| Вопрос и точный сдвиг считаются изменением | «Зачем тут две тумбочки?» → exclude nightstand; «сдвинь на 20 см» → min_clearance | примеры question / unsupported; для точного сдвига — проверка кодом |
| Одно правило вместо двух | «кресло у окна» → только near | в промпте «X у окна → near и require»; в брифе require дописывается кодом |
| Противоречивые правила | move + exclude одного предмета; require для переставляемой стиралки | `reconcile()` в `edit_agent.py` убирает такие сочетания |

Сбоев JSON не было ни разу: с `format=schema` Ollama не даёт модели отступить от схемы.
Все ошибки — смысловые.

## Ограничения

- Правки только к расстановке. Правки плана и перепланировки появятся с шагом 2.
- `facing` («диван напротив ТВ») и `against_wall` как мягкое правило солвер пока игнорирует
  и сообщает об этом в заметках к комнате.
- «Сдвинь на 20 см» не поддерживается: солвер работает с правилами, а не с точными сдвигами.
  Такая правка — `unsupported`.
- Агент правок видит только списки комнат и предметов, без картинки. Комментарий «вот этот стол»
  понятен, только если интерфейс передал `--target`.
- Набор для оценки маленький и размечен нами. Для отчёта его стоит расширить реальными
  формулировками однокурсников.
